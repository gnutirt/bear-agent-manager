# Training Games

Used by: `activity-designer`. A subset of `activity-patterns.md` for
explicitly game-framed activities (guessing games, quizzes, review games,
team competitions).

## When a game is the right choice

- Retrieval practice at the start or end of a session/course.
- Re-energizing after a long explanation block or before/after a break.
- Reinforcing terminology/definitions where the primary challenge is recall,
  not deep reasoning.

## When a game is the wrong choice

- The learning objective is a skill (debugging, building, analyzing) rather
  than recall — use a build challenge, case study, or practical exercise
  instead.
- The class size or delivery mode makes the game mechanics impractical
  (e.g. a buzzer-style competition in a 3-person async-online session).
- It would be the third game-framed activity in the same course without a
  change of format — vary the mechanic (quiz → guessing game → review game),
  don't repeat the identical structure.

## Lightweight game formats

| Format | Mechanic | Good for |
|---|---|---|
| Guessing game | Present a partial result/output, learners predict the rest | Priming intuition before a demo |
| Quiz (rapid-fire) | Short answer/MCQ, timed, individual or team | Terminology, factual recall |
| Review game (jeopardy-style) | Categories × point values, team-based | End-of-session or end-of-course recap |
| Two truths and a bug | Present 3 code snippets/statements, 1 wrong, spot it | Debugging intuition, error analysis crossover |

Every game still needs: Objective, Duration, Participants, Materials,
Instructions, Expected Outcome, Debrief, Difficulty — do not treat "it's a
game" as license to skip these fields.
